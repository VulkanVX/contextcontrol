# ContextControl v0.5.4

Local models can now adapt their allocation to system RAM, CPU cores and GPU memory instead of treating VRAM as the only capacity limit.

- **Auto adapt to hardware:** a saved master toggle in Settings → LLMs and the catalog, with separate switches for GPU layers, context and CPU threads. Managed runtimes can opt out individually. Manual values are retained when Auto is disabled.
- **Managed GGUF runtimes:** llama.cpp and KoboldCpp read bounded GGUF metadata to estimate GPU layers, KV-cache memory and context. Available RAM/VRAM and configurable reserves inform the next start. Preview allocation reads metadata without downloading or loading weights.
- **Ollama and Transformers:** Ollama retains native dynamic GPU placement and receives the selected CPU/context budget. The managed Transformers bridge adapts CPU threads and uses conservative context; it remains CPU-only and its checkpoint memory is not verified by this estimator.
- **Adapted catalog:** fit includes CPU/RAM fallback and partial GPU offload. Rows show estimated RAM/VRAM and context. VRAM threshold filters use the adapted allocation. Unknown sizes, cloud services, external servers and specialized runtimes are distinguished from verified local capacity estimates; Show all retains access to every entry.
- **Stable requests:** available RAM is checked before preparing local chat context; managed starts recheck hardware. Active generations are not reconfigured, and connected managed models retain their actual running context until restarted.

Validation includes allocation boundaries, missing metadata, CPU-only systems, free-memory pressure, GGUF reading, saved toggles, manual-value preservation, catalog filters and actual settings bindings. Live checks used existing weights with llama.cpp, KoboldCpp, Ollama and CPU Transformers. The small Transformers test model echoed a supplied word; these are integration checks, not general model-quality evaluations.

On the release laptop (Ryzen 5 5600H, 4 GiB RTX 3050 Ti, approximately 64 GiB RAM), one warm llama.cpp comparison with Granite 3.3 2B generated 64 tokens from the same prompt in 3.70 seconds with the existing CPU-only defaults versus 2.03 seconds with Auto (27 GPU layers, five CPU threads, 8K context versus the manual 4K context). This is a short end-to-end sample, including prompt processing, not a universal speed guarantee.

Memory estimates can differ from actual runtime allocations. CPU offload enables larger models but can be slower than full GPU execution. Auto does not install model weights, remotely configure external servers, or establish architecture support. Releases are built locally without GitHub Actions.
